# MyGPT tokenizer — design, corpus and training

> **Stage 2.1 candidate (committed, not adopted):**
> the same 32,768 ids with eight conversational specials reserved at the top and a
> code-enriched corpus. See `docs/tokenizer_stage2.1_report.md`,
> `docs/tokenizer_special_tokens.md` and `docs/chat_template.md`. The document
> below describes the shipped Stage 2 tokenizer.

Stage 2 replaces the 260-entry placeholder vocabulary from Stage 1 with a trained
32,768-entry byte-level BPE tokenizer. The model architecture, parameter count
(495,799,296) and embedding matrix (32,768 × 1024) are unchanged: only the
meaning of the ids changed.

## 1. Why byte-level BPE, and why this implementation

| Option | Fit for this project | Verdict |
|---|---|---|
| **Byte-level BPE, GPT-2 style (chosen)** | Already the Stage 1 format; llama.cpp's `tokenizer.ggml.model = "gpt2"` implements exactly this; lossless for any UTF-8 input; no unknown-token failure mode | used |
| SentencePiece BPE (Llama/SPM style) | Would need a different GGUF tokenizer model, `▁`-marker decoding and NFKC normalisation, which rewrites user text and changes the id space mid-project | rejected |
| HF `tokenizers` BPE at runtime | Adds a Rust dependency to the inference path and a second implementation that llama.cpp must agree with | rejected as runtime, used as *trainer* |

The runtime tokenizer stays the dependency-free `tokenizer/tokenizer.py` written
in Stage 1. Training uses the Rust `BpeTrainer` from Hugging Face `tokenizers`
because a pure-Python trainer takes hours for 32k merges, while the Rust one
trains in 113 seconds. The two are reconciled by construction and by test: the
script converts HF's merge list into this project's id space and asserts that
every id maps to the same byte string in both. Parity is then re-checked
end-to-end against llama.cpp (§6).

## 2. Vocabulary layout

| Ids | Content | Count |
|---|---|---|
| 0–3 | `<pad>`, `<bos>`, `<eos>`, `<unk>` | 4 |
| 4–259 | raw bytes 0x00–0xFF | 256 |
| 260–32767 | BPE merges, in rank order | 32,508 |
| **total** | | **32,768** |

Special tokens (also recorded in `tokenizer/special_tokens_map.json` and
`config/model_config.json`):

| Token | Id | Role |
|---|---|---|
| `<pad>` | 0 | padding, unused by the model today |
| `<bos>` | 1 | optional sequence start (`encode(..., add_bos=True)`) |
| `<eos>` | 2 | sequence end, generation stop token |
| `<unk>` | 3 | never emitted (byte fallback covers all input) |

No chat/instruction tokens are reserved yet. When instruction tuning starts it
should reuse `<bos>`/`<eos>` plus plain-text role markers, or a new token must
replace an unused merge id — the vocabulary is full, so this is a deliberate
decision to make before Stage 3 rather than a free slot.

## 3. Corpus

Sources, licences and processing are recorded in
`tokenizer_training/manifests/corpus_manifest.json`, which is generated by the
preparation script (the corpus itself is not committed).

| Source | Licence | Text used | Why |
|---|---|---|---|
| `Salesforce/wikitext` (wikitext-103-raw-v1) | CC BY-SA 3.0 | 510.3 MiB | encyclopedic prose, numbers, technical vocabulary |
| `manu/project_gutenberg` | Public domain | 307.9 MiB | books, dialogue, older prose and punctuation |
| `OpenAssistant/oasst1` | Apache-2.0 | 20.0 MiB | conversational English |
| CPython 3.13 standard library | PSF-2.0 | 14.9 MiB | code, identifiers, indentation |
| 44 IETF RFCs (HTTP, TCP/IP, mail, TLS, URIs, JSON, CSV) | IETF Trust (free to reproduce) | 5.7 MiB | technical prose, URLs, abbreviations, tables |
| **total** | | **849.2 MiB**, 226,616 documents | |

Processing (`tokenizer_training/prepare_corpus.py`):

1. Unicode NFC, CRLF→LF, C0 control characters removed, trailing spaces
   stripped, 3+ newlines collapsed to 2. No case folding, no NFKC: the tokenizer
   must see what users type.
2. Documents shorter than 100 characters or with more than 5% non-ASCII
   characters are dropped (English-only tokenizer).
3. Exact-duplicate documents are removed by SHA-256 of the normalised text:
   1,979 duplicates dropped.
4. Deterministic split: every 100th document goes to the held-out evaluation
   file (2,289 documents, 9.59 MiB), the rest to the training shards.
5. Parquet sources store one line/utterance per row, so consecutive rows are
   merged into ~2,000-character documents before dedupe and splitting.

This corpus is for tokenizer training only. It must not be reused as the
language-model pretraining corpus (see `docs/training_plan.md`).

### Corpus-size pilot

Three tokenizers were trained with identical settings on nested subsets and
scored on the same held-out text:

| Training text | Merges learned | Held-out compression |
|---|---|---|
| 24.3 MiB (5 MiB/source) | 32,508 | 4.458 bytes/token |
| 80.0 MiB (20 MiB/source) | 32,508 | 4.535 bytes/token |
| **849.2 MiB (full)** | 32,508 | **4.650 bytes/token** |

All three fill the vocabulary, so corpus size shows up as compression quality,
not vocabulary completeness. The gain is +1.7% for 3.3× more data and +2.5% for
35× more data — clearly diminishing but still positive, and the full corpus was
already downloaded. Conclusion: **a few hundred MiB is enough for a 32k English
BPE; the 849 MiB set is used because it costs nothing extra and helps technical
and code tokens.** Larger corpora would mainly improve rare-word handling, not
the vocabulary size.

## 4. Training

Settings: byte-level BPE, GPT-2 pre-tokenization regex (`add_prefix_space=False`,
`use_regex=True`), `vocab_size=32764` inside the trainer (256 bytes + 32,508
merges), `min_frequency=2`, `initial_alphabet` = all 256 byte tokens.
Training took 112.9 s on 4 vCPUs and is deterministic for a pinned
`tokenizers` version: two runs on the same corpus produce byte-identical
artifacts (asserted in `tests/test_tokenizer_training.py`).

Reproduce:

```bash
pip install -r requirements-tokenizer.txt          # tokenizers==0.23.3, pyarrow

python3 tokenizer_training/prepare_corpus.py \
    --out-dir /workspace/corpus/processed \
    --manifest tokenizer_training/manifests/corpus_manifest.json

python3 tokenizer_training/train_tokenizer.py \
    --corpus /workspace/corpus/processed/train \
    --out tokenizer --vocab-size 32768 \
    --corpus-manifest tokenizer_training/manifests/corpus_manifest.json

python3 tokenizer_training/evaluate_tokenizer.py \
    --tokenizer tokenizer \
    --eval-text /workspace/corpus/processed/eval/heldout.txt \
    --hf-model /tmp/tokenizer_train/tokenizer.json \
    --json-out tokenizer_training/manifests/tokenizer_eval.json
```

`tests/test_tokenizer_production.py::test_manifest_hashes_match_artifacts`
fails if any artifact is edited without retraining, and
`tests/test_tokenizer.py::test_no_pretrained_artifacts_used` fails if a foreign
tokenizer file appears in the repository.

## 6. GGUF / llama.cpp integration

`tools/export_gguf.py` writes `tokenizer.ggml.model = "gpt2"`,
`tokenizer.ggml.pre = "gpt-2"`, the 32,768 token strings in GPT-2 byte-unicode
form, their types, and the 32,508 merges as `"left right"` token strings (the
form llama.cpp parses). Two Stage 1 bugs were fixed while wiring this up:

1. merges were written as numeric id pairs instead of token strings — invisible
   before, because the Stage 1 tokenizer had no merges;
2. `attn_q`/`attn_k` weights were exported without the RoPE layout permutation
   that converts this project's `rotate_half` (HF-style) convention to ggml's
   interleaved `rope_norm` convention. The model still ran, but logits differed
   from the PyTorch reference (cosine 0.982). With the permutation the F16 GGUF
   matches PyTorch to cosine 0.999999 and greedy decoding is token-for-token
   identical.

Verification: `python3 scripts/verify_gguf_parity.py --gguf dist/mygpt-0.5b-f16.gguf`.

## 7. Known limitations

- **English only.** Non-Latin scripts fall back to byte tokens (1.1–2.0
  characters/token). That is lossless but expensive; a multilingual vocab would
  need a different corpus and would take ids away from English.
- **Code coverage is thin** (14.9 MiB). Common identifiers such as `model` and
  `batch` still split (`mod|el`, `b|atch`). More code in the corpus would fix
  this at the cost of natural-language compression.
- **Whitespace runs**: ~15 merge slots went to 43–51-space indentation tokens
  learned from Python sources. Harmless but not useful.
- **Vocabulary is full.** Adding chat tokens later requires replacing merge ids
  (retraining) rather than appending.
- **No chat template** is embedded in the GGUF yet.
- Tokenizer quality beyond compression (e.g. effect on downstream loss) can only
  be measured after pretraining.
